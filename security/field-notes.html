封存研究筆記：拆解前端密碼鎖

這份筆記是為了教你理解「前端驗證為何不是真正的安全邊界」。請只對這個自己提供的練習頁面操作，勿用於未經允許的網站或帳號。

重要觀念：本頁不是教你入侵別人的帳號。靜態網頁的程式碼本來就會交給瀏覽器，所以不要把真正的秘密放在前端。

先自己推理

  1. 網頁的表單提交後，哪一段 JavaScript 會執行？
  2. 它是把輸入送到伺服器，還是在瀏覽器本機比較？
  3. 為什麼「把密碼藏在 HTML 裡」並不能保密？
線索 A：查看自己這個練習頁面的原始碼

在你有權檢視的練習頁面按右鍵選「檢視網頁原始碼」，或使用瀏覽器開發者工具的 Sources 面板。尋找表單的 submit 事件、雜湊函式和比較條件。

線索 B：理解雜湊比較

練習頁面先將輸入文字轉成 SHA-256 雜湊，再與程式中的預期雜湊比對。雜湊不是加密：它沒有用來還原原文的解密金鑰，但弱密碼仍可能被猜測並逐一計算雜湊比對。

線索 C：為什麼這個鎖仍不安全？

因為驗證程式、預期雜湊和結果顯示都由使用者控制的瀏覽器執行。這個示範的目標是學習，不是保護真實資產。真正的系統必須在伺服器端驗證，並搭配適當的密碼儲存方案、限速、監控與多因素驗證。

最後解答：這個示範的通關字串

本教學專用的虛構答案是：Nebula!47-Quartz#Mango

請勿把這個字串用作任何真實帳號密碼。這個答案只用來確認你理解了本練習的流程。

安全設計清單

  • 不要在前端原始碼放秘密或 API 金鑰。
  • 伺服器端驗證權限，避免只靠隱藏按鈕或前端判斷。
  • 使用專門的密碼雜湊方案（例如 Argon2id、scrypt 或 bcrypt），不要直接以快速 SHA-256 儲存使用者密碼。
  • 實作限速、多因素驗證、登入通知與安全的密碼重設流程。
